    PMX 常见问题

    为什么我需要使用 PMX？

    因为：

    • PMX 将所有分散（或无法获取）的权限相关信息和控件整合到单一界面，让您能够全面、便捷地查看和管理它们。
    • 原生安卓系统中没有官方工具可用于更改 AppOps。系统权限设置中只会向用户展示部分清单权限。PMX 以原始形式暴露所有权限。相关阅读："清单权限与 AppOps"。
    • PMX 让您轻松追踪权限的任何不受欢迎的更改。
    • 通过控制您的设备，PMX 能帮您节省设备资源（如电池电量和网络带宽），并保护您的隐私。您不再完全受制于应用和 ROM 开发者的摆布。阅读这篇文章可获得直观认识。
    • PMX 能实时监视权限变更，并在您停止使用应用时自动撤销这些权限；它也可以执行权限的定期扫描，让您不必记住一切。
    • PMX 让您轻松备份和恢复已安装应用的权限状态，无需反复调整应用权限。

    另请参阅"什么是 PMX？"

    为什么 PMX 需要 root 权限或 ADB 访问权限？

    安卓系统有意限制应用修改其他应用的清单权限或 AppOps 权限（很多情况下也限制修改自身部分权限），这些限制是为了保护用户隐私和系统完整性。

    为了执行需要提升权限的操作，PMX 采用独立的小型特权辅助程序，而不是尝试通过常规应用进程完成所有操作。默认情况下，该辅助程序通过 ADB 启动时以 ADB 用户标识（2000）运行；在已获取 root 权限的设备上则以系统用户标识（1000）运行。如果您的设备已 Root，可以在高级设置中更改辅助程序的 UID。

    设备尚未 Root，如何使用 PMX？

    通过 ADB 使用 PMX。请阅读开头部分的提示——某些设备可能有一些限制。

    为什么 PMX 在最新的安卓系统上无法运行或无法正常工作？

    PMX 依赖安卓的隐藏 API（非 SDK 接口）。这些接口与标准 API 不同，未在安卓开发者文档中记录。因此每次安卓新版本发布后，我们必须通过安卓源代码来了解哪些 API 已损坏（被更改或删除）。

    此外，修复损坏的 API 需要时间，有时需要几周，有时需要几个月，而且不能保证我们总能修复它们。有时 Google 有意让我们难以或无法继续使用隐藏 API。

    因此，在最终 AOSP 源代码公开发布（在代码搜索或 Git 仓库上）之前，我们无法让 PMX 立即在每个新的安卓版本（尤其是测试阶段）上运行。

    PMX 应用在其 GitHub 和 Google Play 商店的应用描述中注明了其支持的最高安卓版本。当您第一次在不支持的版本上运行应用时，它会显示类似如下的警告：

    为什么 PMX 在 OEM 操作系统或自定义 ROM 上无法正常工作？

    PMX 依赖安卓的隐藏 API（非 SDK 接口）。这些接口与标准 API 不同，未在安卓开发者文档中记录，因此我们需要访问您 ROM 的源代码，才能准确了解这些隐藏 API 的工作原理。

    值得庆幸的是，AOSP（由 Google 开发）是开源的。但如果您的原始设备制造商（OEM）或 ROM 开发者为定制目的修改了 AOSP，我们无法确切知晓他们对原生 AOSP 代码做了哪些改动。对此我们确实无能为力。这一事实已在 GitHub 和 Play 商店中的应用描述中说明。抱歉。

    PMX 如何更改其他应用的权限？

    PMX 本身既不能也无法授予或撤销其他应用的权限。事实上，没有任何第三方应用有权这样做——控制应用权限的是安卓操作系统本身。PMX 只是向安卓框架发送更改权限状态的请求，是否响应完全取决于安卓系统。并非所有权限都可以更改。如果您无法通过 PMX 修改某项权限状态，那么通过其他任何方式也无法实现。

    关闭 ADB、拒绝 root 权限或卸载 PMX 后，权限设置是否仍保持更改后的状态？

    同上：控制应用权限的是安卓操作系统。一旦权限被更改，无论您卸载 PMX 还是撤销其特权，都不会产生任何影响。除非您或安卓系统再次修改，否则该权限将一直保持您所修改的状态。

    为什么不能更改某些权限？

    只有危险保护级别（以及其他少数）的清单权限可以更改。AppOps 是否可以更改取决于它依赖的其他 AppOp。这就是安卓的工作方式，我们无法改变其行为。参见"清单权限与 AppOps"。

    此外，PMX 保护着若干关键框架应用和权限，修改它们可能导致设备变砖。参见相关问题。

    另请参阅"为什么某些 AppOps 无法更改？"

    请注意：从安卓 15 开始，带有开发保护级别的系统应用的清单权限将无法撤销——安卓会静默忽略该请求。

    我已经更改了权限，但没有效果。为什么？

    成功更改权限后，如果您没有得到预期的结果——例如它立即还原，或在几小时或几天后恢复——那要归咎于安卓操作系统。请查看：

    • PMX 如何更改其他应用的权限？
    • 为什么某些 AppOps 无法更改？

    当您使用应用时，安卓系统可能会更改它们的权限。很遗憾，对此我们无能为力。"权限监视器"和"定期检查"在这方面或许能帮上忙。

    为什么某些 AppOps 无法更改？

    有时您会看到"AppOp 模式未更改"的提示，这意味着安卓拒绝了更改 AppOp 模式的请求。无论使用何种方法或应用，您都无法更改它。原因可能有多种：

    • 某些 AppOps 依赖其对应的清单权限，因此无法独立更改。例如，若已授予 android.permission.READ_CONTACTS 清单权限，就无法拒绝 READ_CONTACTS 这个 AppOp。
    • 如果应用未在其清单文件中请求某清单权限，其对应的 AppOp 也无法被授予。但如果应用尝试使用它（并被拒绝），它仍可能出现在应用的权限列表中。SYSTEM_ALERT_WINDOW 就是一个例子。
    • 某些 AppOps 仅用于兼容性（例如 LEGACY_STORAGE），实际上并不控制任何功能。若您了解其工作原理，就会明白授予 / 撤销这类权限毫无意义。
    • 某些权限在应用正在运行时，或应用面向较旧 / 较新版本的安卓时，无法更改。
    • 某些 OEM 的 ROM 在处理 AppOps 时表现异常。参见"为什么 PMX 在 OEM 操作系统或自定义 ROM 上无法正常工作？"

    例如，在搜索框中输入 _CLIPBOARD（并勾选深度搜索），即可找到所有曾使用（或尝试使用）READ_CLIPBOARD 或 WRITE_CLIPBOARD 权限的应用。时间戳也会显示（但并非所有 AppOps 都显示）。

    因此，如果您关注的应用没有出现在搜索结果中，请在上述排除过滤器列表中同时勾选对应的 AppOps。

    在高级设置中，我应该选择哪个特权守护进程 UID？系统还是 ADB？

    这仅在您使用 root 权限时才重要（或者您设备上的 adbd 以 root 权限运行，最终用户设备通常不是）。

    建议使用系统（UID 1000），因为它比 ADB（UID 2000）权限更高。例如，只有以系统身份运行时才能更改"系统固定"的权限。

    排除过滤器中的"无效权限"指什么？

    如果某个应用请求了清单权限，但该权限既未在安卓框架中声明（提供），也未在任何已安装的软件包中声明（提供），则该权限属于无效权限。例如，如果您的设备上没有安装 Play 商店应用，com.android.vending.BILLING 就是一个无效权限。

    排除过滤器中的"额外 AppOps"指什么？

    并非所有 AppOps 都会出现在每个已安装应用的权限列表中。但您可以强制任何应用显示某个 AppOp：选中的额外 AppOps 会出现在所有应用的权限列表中，方便您设置。

    AppOp 有哪些不同的模式？我应该用哪种？

    通常您应该选择"允许"或"忽略"。或者您可能只想在应用处于前台（仅安卓 9 及以上版本）时允许该操作。"拒绝"是"忽略"的加强版，可能导致请求该操作的应用崩溃。"默认"即系统的默认行为，具体表现因 AppOp 而异。

    请注意，并非所有 AppOp 模式都能为每个应用的每个 AppOp 设置。例如在近期的安卓版本中，CAMERA 和 MICROPHONE 只允许用户应用在前台使用（即使模式设置为"允许"）。同样，某些 AppOps 永远无法设置为"仅前台"模式。

    相关阅读："为什么某些 AppOps 无法更改？"；官方文档：AppOpsManager。

    "忽略"和"拒绝"模式有何区别？

    "忽略"会静默失败；"拒绝"会向应用抛出错误，应用可能因未预料到而崩溃。您通常应该使用"忽略"。

    为什么我无法将 AppOp 模式设置为"仅前台"？

    并非所有 AppOps 都能设置为"仅前台"模式。即使设置成功，也可能无法提供预期的结果。

    相关阅读："AppOp 有哪些不同的模式？我应该用哪种？"、"为什么某些 AppOps 无法更改？"

    请注意，权限模式"仅在使用应用时允许"并不总是把 AppOp 模式设为"仅前台"：

    通常我们只看到清单权限的两种状态：已授予和已撤销。但安卓使用标志（flags）把这两种状态细分成多个子状态。对某些权限来说，"仅当应用可见时才授予"的行为正是通过这一机制实现的——此时 AppOp 权限并未参与。

    更多详情请参阅官方文档中的"后台访问"和"前台访问"。

    为简化起见，PMX 目前不监视权限标志，但将来可能会添加一个选项来跟踪权限标志的更改（即使授予 / 撤销模式保持不变）。

    WAKE_LOCK 权限的作用是什么？

    应用通过持有唤醒锁（Wake Lock）来保持设备唤醒，也就是不进入 Doze 模式。

    如何修改 INTERNET 权限？

    安卓不允许修改所有权限，例如普通保护级别的权限（如 INTERNET），或带有固定标志、签名保护级别的权限（通常是系统或框架应用）。参见"清单权限与 AppOps"。

    不过，如果您的设备已 Root，Fyrypt 可以让您非常有力地控制设备上的网络活动。

    "固定"权限是什么？

    "系统固定"权限由原始设备制造商（OEM）或 ROM 开发者授予预装应用，它们本不该被更改。但如果您的设备已 Root，PMX 可以修改系统固定权限。

    "策略固定"权限由管理设备的 IT 管理员授予（或拒绝），它们不能被更改。

    "用户固定"权限由用户固定下来：如果用户多次拒绝某个应用请求的权限，系统会将该权限标记为用户固定，应用再次请求时不会再询问。用户可以随意更改这种固定权限。

    如何更改系统固定权限、签名 / 特权权限或框架应用的权限？

    如果您的设备已 Root，在付费版中可通过高级设置中的"允许关键更改"选项，修改带有系统固定标志、签名或特权保护级别的权限，以及框架应用的权限。但不建议拿系统和框架应用做实验——您可能会让设备变砖。

    AppOp 权限中的"UID 模式"指什么？

    这是 AppOp 权限的一种作用模式，表示修改此 AppOp 时，也会影响其他具有相同 UID 的已安装应用。参见 sharedUserId。

    请注意，对许多 AppOps 来说，UID 模式优先于包模式。

    我能通过 PMX 控制安卓"若应用未被使用则移除权限"功能吗？

    可以。此功能自安卓 11 起可用，在某些设备上也被称为"暂停未使用的应用活动"。

    用 PMX 设置此选项的方法：

    1. 前往 排除过滤器 → 额外 AppOps 列表，勾选 AUTO_REVOKE_PERMISSIONS_IF_UNUSED。
    2. 返回主屏幕，在顶部搜索栏输入 AUTO_REVOKE_PERMISSIONS_IF_UNUSED。请确保在搜索设置中启用了深度搜索。
    3. 为想要的应用设置"允许"或"忽略"模式。

    您也可以用"权限视图"或"批量操作"代替第 2、3 步。下面是使用批量操作的指南：

    为什么我总收到大量"Bad ROM"弹窗？

    设备制造商对 AOSP 代码（由 Google 开发）做了大量更改，因此在某些定制 / OEM 设备上，AppOps 框架会返回出乎意料的结果，PMX 无法理解。您可以忽略这些警告，但部分功能可能失效。

    您可以在 设置 → 常规设置 中关闭"Bad ROM"通知。

    参见"为什么 PMX 在 OEM 操作系统或自定义 ROM 上无法正常工作？"

    "从列表中隐藏"（长按弹出）功能有何作用？

    它们都是把应用或权限从可见列表中隐藏。如果您不想更改某个应用的任何权限，可以隐藏它，它将不再出现在任何应用中。要取消隐藏，请回到排除过滤器设置。

    同样，如果您不关心某个应用的权限，也可以把它排除在可见列表之外。

    是否有包含所有权限及其说明的完整列表？

    据我所知，没有完整的权限描述列表。PMX 专业版会显示常见清单权限和 AppOp 的简要说明。

    还有一些第三方资源，比如 Izzy 的这个。安卓官方开发者网站和源代码也是很好的学习来源。

    每个新的安卓版本都会添加一些新权限，有些权限会过时；而且并非所有权限都需要每个用户去处理。

    如何在工作资料 / 多用户环境中使用本应用？

    专业版支持工作资料和多用户，从下拉菜单中选择一个用户即可。

    PMX 与 XPrivacyLua 相比如何？可以相互替代吗？

    PMX 并非旨在取代 XPrivacyLua 之类的项目，而是与之互补，它们的设计目标不同。

    XPrivacyLua 通过钩入内部 API 来"破解"安卓的标准功能：使用 Xposed 将部分安卓库替换为修改后的版本，从而获得额外的能力，例如向应用提供虚假数据，以及接收权限相关事件的通知——这些通过其他正常手段是无法得知的。

    PMX 则不是作为框架模块设计的。它只是便捷地访问某些普通应用无法使用的特权 API，不会以任何方式修改安卓系统的标准功能。PMX 执行的大多数任务也可以通过命令行完成，少数操作除外，例如修改系统固定权限。

    使用 XPrivacyLua 有两个硬性要求：root 和 Xposed。PMX 两者都不需要。对许多设备来说，root 和 Xposed 要么不可用，要么由于技术难度、保修失效、SafetyNet 失效等问题，让许多用户望而却步。

    更多说明见这里和这里。

    PMX 能否像 Bouncer 那样在应用关闭时自动撤销权限？

    可以，参见"权限监视器"和"定期检查"。但它不使用安卓的无障碍功能来替用户在屏幕上点击（尽管那是个无需额外设置的好功能）。PMX 依赖 root 或 ADB 权限，因此能实现的功能远超无障碍所能提供的（详见"什么是 PMX？"）。

    如果您使用 ADB 且未 Root，权限监视器在某些设备上可能无法正常工作，请参阅"ADB 的限制"。

    安装新应用时是否有通知提示？

    有，请参阅"权限监视器"。

    由于安卓 8 不允许后台应用获知新安装应用的事件，我们必须运行一个前台服务（持续通知）才能接收此事件。或者，您也可以考虑使用"定期检查"。

    安装新应用时，PMX 能否默认取消其权限？

    可以，但没有"权限删除"：所有可撤销的清单权限都会被撤销，并保持撤销状态，除非用户明确授予。就 AppOps 而言，其中许多（如 VIBRATE 和 READ_CLIPBOARD）至少要到应用使用一次后才会出现；而且如上所述，许多对应的清单权限（如 READ_CONTACTS）已被撤销，因此应用安装时无法预知应该移除哪些 AppOps。

    不过，安装新应用时会显示通知（若使用权限监视器），用户可以逐项设置权限或应用配置文件。

    为什么 PMX 需要互联网权限？

    独立的专业版需要联网验证许可证。其他版本可以完全离线工作（Play 商店版也需要联网验证许可证）。

    本地（设备内）使用 android.permission.INTERNET 权限：

    安卓系统不允许应用在未获得 INTERNET 权限的情况下创建网络套接字，即使这些套接字仅用于本地操作而非互联网连接。PMX 的本地（设备内）连接（即在 127.0.0.1 创建 localhost 套接字）有两个用途，都是进程间通信（IPC）：

    • PMX 启动一个具有 root / ADB 特权的后台进程，并通过网络套接字与其通信。初始握手后，两个进程改在 Binder 上通信。我们没有更好的办法，因为安卓系统不允许应用使用 UNIX 域套接字。
    • 如果您的设备未 Root，且通过 ADB 使用 PMX，连接 adbd 需要 INTERNET 权限。

    因此，如果应用无法创建或使用本地网络套接字，它就会失效。若想阻止 PMX 访问互联网，必须确保该应用仍能通过回环接口与设备上的进程通信。基于 iptables 的防火墙（如 Fyrypt）和基于 VPN 的防火墙（如 NetGuard）通常会出现这种情况。但某些 ROM 内置的禁止网络访问功能会同时阻止应用使用互联网，并禁用其为 IPC 创建回环套接字的能力。因此，如果拒绝此权限，PMX 将无法获得 root / ADB 权限。

    PMX 对隐私的友好程度如何？你们是否收集用户数据？

    否。我们不收集您的数据，永远不收集，一个字节都不收集。PMX 有开源版本。我们坚信用户应当充分了解 PMX 为何需要相应权限。我们尊重您的隐私，从未收集过任何数据，甚至包括崩溃日志。您也可以查看我们的隐私政策。

    PMX 是否通过 ADB 在网络上监视我？

    否。

    PMX 通过本地主机（127.0.0.1）与 adbd 进程通信。但 adbd 无法只监听本地主机而不监听其他网络接口（因为 ADB 本来就要在外部电脑上使用）。如果可以的话，您完全可以阻止 adbd 监听外部 IP 地址——PMX 仍可正常运行，且无需向外部暴露任何端口。

    此外，您可以在高级设置中把 5555 端口改成任意数字，它不是硬编码的。

    另外，自安卓 4.2 起，ADB 通过 RSA 密钥认证（最强大的认证机制之一）进行保护。因此，即使设备可从互联网访问（这种情况极不可能发生），未经身份验证的任何人也无法建立 ADB 连接。

    欢迎以任何方式验证这些说法。我们随时为您提供技术支持。

    PMX 是否滥用 root 权限收集我的数据？

    我们坚信最小权限原则。但由于安卓操作系统的限制，PMX 没有高权限就无法运行。我们能做的是：如果您技术娴熟，我们可以教您如何让应用难以联网，即使它拥有 root 权限。

    我认为 PMX 毫无用处，你们为什么要开发这个软件？

    我们尊重您的意见。PMX 并不适合所有人（正因如此，它多年未打磨发布，因为我们深知受众极其有限）。它只适合那些格外关注自身隐私和设备控制的极客用户。大多数手机用户任由设备制造商和应用开发者摆布，他们不知道这些人和自己的数据做了什么。多数人更看重便利而非隐私——这没什么不好。
